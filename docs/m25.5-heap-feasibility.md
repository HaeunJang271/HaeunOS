# M25.5 Heap Feasibility

Date: 2026-11-16  
Prerequisite audit: [m25.5-memory-layout-audit.md](m25.5-memory-layout-audit.md)

## Verdict

**Feasible** to add a **fixed-region, per-slot user heap** (initially one 4 KiB page) without growing AS×3, without moving the 4 KiB stack, and without breaking M25.4 guards — **if** M25.6 reserves unused VA/PA and extends SPAWN/FORK/scrub.  

**Dynamic-region heap** (grow/shrink by page, guest PMM) is **not** appropriate for the next milestone: process-v1 has no page freelist, and identity-map / FORK memcpy assumptions would expand sharply.

This document does **not** claim an allocator is implemented.

---

## A. Fixed-region heap

### Sketch (illustrative; final numbers in M25.6 proposal)

- Shared user **VA** for heap base (same in every AS), e.g. one page in the unused `0x00109xxx` band (not code `0x108`, not guards `0x112`/`0x113`/`0x114`, not stacks).  
- Per-slot **PA** from unused frames (e.g. distinct pages in `0x0010Exxx`..`0x00111xxx` or above `0x116000` below kstacks `0x124000` — must be proven free at implement time).  
- PTE: U\|RW (`0x17`), installed at boot and/or SPAWN.  
- Max size = reserved region (start with **4 KiB** to match code/stack granularity).

### Pros

- Matches existing static-slot philosophy (code + stack).  
- FORK = one more page memcpy (same pattern as `fork_user_mem`).  
- Scrub = `memset` reserved PA + optional PTE clear.  
- Isolation = distinct PA; MMU already enforces U/RW.  
- No COW; no PMM.

### Cons

- Hard cap; fragmentation inside the arena.  
- Consumes scarce low-memory identity space; must not collide with FORK helper maps.  
- Slot2’s guard/identity use of `0x114000` shows adjacent-page PTE choices are delicate.

### Collision checklist

| Risk | Mitigation |
|------|------------|
| Code `0x108000` | Heap VA ≠ code page |
| Stack / guard | Heap VA outside `[0x112000,0x116000)` stack/guard band **or** carefully above `0x116000` with per-slot VA (worse for pointers) |
| `fill_k` identity | Do not reuse PAs that other slots need as kernel identity without U |
| PTE exhaustion | One extra leaf per AS is fine (1024-entry L0) |

## B. Dynamic-region heap

### Sketch

- `brk`/`mmap`-style growth; allocate free physical frames; install/clear PTEs; maybe unmap on `free` of whole pages.

### Pros

- Scales with app need; better long-term UNIX-like model.

### Cons (vs current HAEUN-OS)

- Requires **page allocator** (guest or host-assisted) — absent in process-v1.  
- FORK must copy **variable** number of pages or introduce COW (forbidden now).  
- Rollback on partial map failure is harder than fixed wipe.  
- Interaction with `fill_k` identity windows and scrub becomes a moving target.  
- Larger ABI surface (`brk`, faults on grow).

### Impact rating

| Concern | Fixed | Dynamic |
|---------|-------|---------|
| AS×3 / stack / guard preserve | Low risk if placed carefully | Medium–high |
| PTE / AS capacity | Low | Medium (many leaves) |
| FORK policy | One page copy | Multi-page or COW |
| EXIT scrub | Fixed memset | Walk mappings |
| SPAWN/FORK rollback | Same as today + one region | Complex |
| Cross-process isolation | Natural (PA) | Natural if PTEs correct |
| Fit for M25.6 | **Yes** | **Defer** |

---

## Recommendation

Adopt **Fixed-region heap** for any M25.6 implementation attempt; keep region size at **one page** until apps prove need. Defer dynamic growth and COW. If even fixed placement cannot find collision-free PA/VA without rewriting `fill_k`, **defer heap** rather than weaken guards or FORK.
