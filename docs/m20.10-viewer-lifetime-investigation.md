# M20.10 Viewer Lifetime Investigation

Date: 2026-11-15  
Mode: **read-only** (no code changes).  
Command: `.\build\haeun-vm.exe build\process_launch.hxf --apps --viewer`

Log:

```text
viewer: frames=1439 keys=1 mice=0 focus_hits=0 focus_id=-1
guest halted after 368150 instructions; r1=0x00000001
```

---

## 1. Viewer 종료 조건

`haeun_vm_viewer_run` (`src/vm_viewer_win32.c`) 루프 탈출 조건은 다음뿐이다.

| 조건 | 코드 위치 | 본 로그와의 관계 |
|---|---|---|
| `haeun_vm_step` → `HAEUN_VM_HALTED` | L265–268 `goto done` | **해당** (`guest halted` + `r1=1`) |
| `haeun_vm_step` → 기타 비-OK | 동일 | 해당 없음 (halt 메시지 출력됨) |
| `plat.quit != 0` (창 닫기) | L261, `wnd_proc` `WM_DESTROY` | mice/keys만으로는 판단 불가; halt가 있으면 게스트 종료가 충분 설명 |
| `*steps_executed >= max_steps` | L261, L273–274 → `HAEUN_VM_STEP_LIMIT` | **해당 없음** — budget `INSTRUCTION_BUDGET` = 10_000_000 (`main.c`); 실행 368_150 ≪ budget |

`done:` 라벨에서 **항상** Win32 창을 파괴한다.

```text
refresh_fb(&plat);
DestroyWindow(plat.hwnd);   /* vm_viewer_win32.c L276–278 */
…
return st;
```

따라서 viewer 수명은 “게스트가 멈추거나 / 창을 닫거나 / step budget 소진”과 같고, halt 시에는 **즉시** 호스트 창이 사라진다.

## 2. Guest halt → Viewer 종료 (직접 유발)

**예. 직접 유발한다.**

호출 연쇄:

1. Guest `halt` 또는 halt를 유발하는 경로  
   - ISA: `HAEUN_OP_HALT` → `haeun_cpu_set_halted(true)` → `HAEUN_VM_HALTED`  
     (`src/instruction_executor.c` L41–46)  
   - 또는 마지막 프로세스 `sys_exit`에서 READY 없음 → `halt`  
     (`kernel/process/proc_sys.s` `sys_exit` L28–34)
2. `haeun_vm_step` / `haeun_vm_run` 이 `HAEUN_VM_HALTED` 반환 (`src/vm.c`)
3. `haeun_vm_viewer_run` 내부 step 루프가 `st == HAEUN_VM_HALTED` 이면 `goto done`
4. `DestroyWindow(plat.hwnd)` 로 GUI 창 제거
5. `main.c` L381–383: `haeun_vm_viewer_run` 반환 후 L404–409 viewer 통계 출력, L423–427  
   `guest halted after …; r1=…` 출력 후 `goto out` → 프로세스 종료

본 로그의 `guest halted` + `r1=0x00000001` 는 이 경로와 일치한다.

## 3. Event loop vs guest execution loop (수명 관계)

단일 스레드 **협력적** 루프 (`haeun_vm_viewer_run`):

```text
while (steps < budget && !quit):
    for i in 0..VIEW_SLICE(256):
        st = haeun_vm_step(vm)    # guest
        if HALTED or error: goto done
    pump()                         # Win32 messages
    refresh_fb()                   # snapshot + blit; frames_drawn++
```

- Guest와 viewer는 **분리된 장수명 프로세스/스레드가 아니다.**
- Guest halt는 viewer 루프의 1급 종료 신호다.
- `frames=1439` ≈ `368150 / 256` → halt 직전까지 slice마다 blit한 횟수와 정합.

별도 “GUI만 유지하는 idle loop”는 **없다.**

## 4. 마지막 앱 종료 후 framebuffer 유지?

| 단계 | 동작 |
|---|---|
| 자식 앱 EXIT | mux `reap_pid` → 창 destroy 가능; FB RAM 바이트는 남을 수 있음 |
| 런처 `paint_ok` + `GFX_COMPOSE` | `gui_launch.s` L127–130: 종료 직전 다시 그림 |
| Guest `SYS_EXIT(1)` + `halt` | `gui_launch.s` L131–134 |
| Viewer `done:` | `refresh_fb` 한 번 더 한 뒤 **`DestroyWindow`** |

즉 RAM상 마지막 프레임은 halt 직전 compose 결과일 수 있으나, **호스트 창은 halt와 함께 닫히므로 사용자에게 “유지된 GUI”로 보이지 않는다.**  
FB를 디스크에 남기려면 `--fb-dump` 등 별도 경로가 필요하다 (`main.c` L410–416). `--viewer`만으로는 창 유지 없음.

## 5. `--viewer`가 “잠깐만 보여주도록” 설계되었나?

**시간 타이머로 GUI를 끄는 설계는 아니다.**

- 표시 길이는 **게스트가 halt할 때까지의 명령 수**에 비례한다.
- `process_launch.hxf` userland (`userland/gui_launch.s`)는 스모크 시퀀스 후 **의도적으로** `EXIT(1)` + `halt` 한다 (L127–134).
- 따라서 “잠깐 보이다 사라짐”은 viewer 버그가 아니라 **런처가 OS(게스트)를 종료하기 때문**이다.
- Step budget(10M)에 의한 조기 종료는 본 로그(368k steps)와 무관.

---

## 6. 앱 종료 vs OS 종료 구분

| 구분 | 메커니즘 | Viewer 영향 |
|---|---|---|
| 자식 앱 EXIT | `haeun_ecall_mux_io` EXIT → `reap_pid` / guest ZOMBIE+WAIT | 창/리소스 회수; **게스트 CPU는 계속** (런처 READY) |
| 런처(게스트 init) EXIT + `halt` | 마지막 READY 없음 또는 `halt` insn | **`HAEUN_VM_HALTED` → viewer 종료** |
| 호스트 `haeun-vm` 프로세스 | `main`이 run 반환 후 `out` | 프로세스 종료 |

앱 종료와 OS(게스트 VM) 종료는 코드상 구분되어 있다.  
현재 `gui_launch.s`는 스모크 끝에서 **OS halt까지** 수행하므로, viewer 수명 = 그 스모크 수명이다.

`r1=0x00000001`: 런처 `addi r2, r0, 1` 후 `SYS_EXIT` — 스모크 성공 코드. `sys_exit`가 READY 없이 halt할 때 PCB exit_code를 `r1`에 올린다 (`proc_sys.s`).

## 결론

| 질문 | 답 |
|---|---|
| 창이 사라지는 직접 원인 | Guest `HAEUN_VM_HALTED` → `haeun_vm_viewer_run` `done` → `DestroyWindow` |
| Halt가 viewer를 끊는가 | **예** |
| 수명 모델 | 단일 협력 루프; guest halt = viewer 종료 |
| FB 유지 | 창은 유지하지 않음; halt 후 DestroyWindow |
| `--viewer` 시간 제한? | 없음; 게스트 halt에 종속 |
| 앱 vs OS 종료 | 구분됨; 본 이미지는 런처가 OS halt까지 진행 |

**분류:** 정상 동작 (스모크 런처 + viewer 결합 설계). 결함으로 단정할 근거 없음.  
지속 GUI가 필요하면 게스트가 halt하지 않도록 런처/idle 정책을 바꾸는 **별도 설계 변경**이 필요하다 (본 문서는 수정하지 않음).
