# M21.1 Persistent Desktop Premature Exit Investigation

Date: 2026-11-15  
Command under investigation (no code changes):

```powershell
.\build\haeun-vm.exe .\build\process_desktop.hxf --apps --persist --viewer
```

## Executive finding

The GUI closes after a few seconds because the **host instruction budget** (`INSTRUCTION_BUDGET = 10_000_000`) is exhausted while the guest desktop idle loop is still running. The viewer then tears down the Win32 window. This is **not** Esc/`EXIT(0)` guest shutdown.

**Classification: `VM_BUDGET_EXHAUSTION`**

---

## 1. CLI `--persist` activation

Evidence: `src/main.c`

| Location | Behavior |
|---|---|
| usage (~L25) | Lists `[--persist]` |
| parser (~L186–189) | `--persist` → `persist_mode = true`, `desktop_mode = true`, `gui_mode = true` |
| apps (~L181–185) | `--apps` → builtins + `apps_mode` (required for calc/edit/…) |
| input script (~L362–363) | `persist_mode` selects M21 script **only if `--input`** |

Live run stdout shows builtin registration and a focused desktop window (`focus_id=0`), with **zero** scripted keys (`keys=0`). That matches `--persist --viewer` **without** `--input`: persist/desktop chrome path active; no Esc injection.

**Ruled out: `CLI_FLAG_NOT_APPLIED`**

---

## 2. `process_desktop.hxf` vs `desktop.s`

| Artifact | Observed (this investigation) |
|---|---|
| `userland/desktop.s` | LastWriteTime `2026-11-15 09:47:24`, 3785 bytes |
| `build/process_desktop.hxf` | LastWriteTime `2026-11-15 10:01:23`, 33588 bytes |

HXF mtime is **newer** than `desktop.s` → not stale by filesystem timestamps.

Guest behavior also matches current `desktop.s` idle loop (no auto-spawn, no early `guest halted`).

**Ruled out: `BUILD_ARTIFACT_STALE`**

---

## 3. `desktop.s` event loop and exit branches

File: `userland/desktop.s`

| Label | Condition | Effect |
|---|---|---|
| `loop` (L29+) | `EVENT_POLL` (ECALL 27) | empty → `idle`; KEY_DOWN(1) → `on_key`; MOUSE_DOWN(4) → `on_mouse`; else continue |
| `idle` (L117–122) | empty poll | `GFX_COMPOSE` (23) then `YIELD` (10) then `jal r0, loop` — **no EXIT** |
| `shutdown` (L214–221) | scancode `0x01` (Esc) | `WIN_DESTROY`, `EXIT` with r1=0/r2=0, `halt` |
| `die` (L223–227) | `WIN_CREATE` failure | `EXIT` r2=`0xe1`, `halt` |
| spawn paths | after WAIT/reclaim | return to `loop` |

With no keyboard input, only `loop` ↔ `idle` runs. There is **no** timeout exit inside the guest.

**Ruled out as primary: `GUEST_LOOP_EXIT`** (guest did not take `shutdown`/`die`)

---

## 4. `EVENT_POLL` / `YIELD` returns

| ECALL | Number (`desktop.s` / `include/haeun/sec.h`) | Idle behavior |
|---|---|---|
| `EVENT_POLL` | 27 | empty → r1=0 → branch `idle` (`m20_ecall.c` writes 0 when queue empty) |
| `YIELD` | 10 | sole READY desktop re-picked by scheduler (`proc_sched.s` `pick_next`) |

Idle path keeps PCB0 runnable; it does not clear READY.

---

## 5. READY / WAIT exhaustion

`kernel/process/proc_sys.s` `sys_exit` (L21–34): halt only when **no READY** after zombie + `wake_all` retry.

Interactive idle: desktop stays READY via YIELD; no child WAIT held open without a prior spawn. Live log has **no** `app-env: spawn …` lines → no WAIT-block deadlock for this run.

Final PC `0x00100b48` is **below** user base `0x00108000` (`tools/build_process_image.py` `USER_VA`) → stop occurred in **kernel** during a syscall slice, consistent with YIELD/compose ecall service—not an empty-scheduler halt with `guest halted`.

**Ruled out: `SCHEDULER_DEADLOCK`**

---

## 6. VM instruction budget / halt vs step-limit

| Symbol / API | Evidence |
|---|---|
| `INSTRUCTION_BUDGET` | `src/main.c` L20: `UINT64_C(10000000)` |
| Viewer entry | `src/main.c` L387–389: `haeun_vm_viewer_run(..., INSTRUCTION_BUDGET, &steps)` |
| Enum | `include/haeun/vm.h`: `HAEUN_VM_STEP_LIMIT` = **6** (after `HALTED=1` … `ALIGNMENT=5`) |
| Viewer budget end | `src/vm_viewer_win32.c` L261–274: loop while `*steps_executed < max_steps`; if OK and budget hit → `st = HAEUN_VM_STEP_LIMIT` |
| Host print | `src/main.c` L429–438: `HAEUN_VM_HALTED` → `"guest halted..."` rc=0; **else** → `"guest stopped with result %u..."` rc=1 |

---

## 7. Viewer teardown / `DestroyWindow`

`src/vm_viewer_win32.c` `haeun_vm_viewer_run`:

1. Cooperative step slices (`VIEW_SLICE = 256`, L9 / L264–268).
2. On `HALTED` **or** any non-`OK` step → `goto done`.
3. Or after budget → set `HAEUN_VM_STEP_LIMIT` (L273–274).
4. **`done:`** always `DestroyWindow(plat.hwnd)` (L277–278) then clear `window_open`.

So the window always closes when `viewer_run` returns—for halt **or** step-limit. Teardown is a **consequence** of the run ending, not an independent viewer timeout.

**Not primary class `VIEWER_EXIT`** (viewer correctly follows host run end).

---

## 8. Esc / `EXIT(0)` without key?

Live log:

- `viewer: … keys=0 …`
- stderr: `guest stopped with result 6 …` — **not** `guest halted … r1=0x00000000`

`shutdown` would require KEY_DOWN scancode `0x01` and would produce halt + typically rc=0 via `HAEUN_VM_HALTED`. Observed path is result **6** / rc **1**.

**Esc/`EXIT(0)` did not run.**

## 9. Actual execution log (this investigation)

Command: `.\build\haeun-vm.exe .\build\process_desktop.hxf --apps --persist --viewer`  
Wall clock until exit: **~2916 ms**, process exit code **1**.

**stdout:**

```text
apps: registered calc (304 bytes)
apps: registered edit (400 bytes)
apps: registered files (272 bytes)
apps: registered svcidle (172 bytes)
apps: registered filemgr (1068 bytes)
viewer: frames=39064 keys=0 mice=0 focus_hits=0 focus_id=0
```

**stderr:**

```text
guest stopped with result 6 at PC 0x00100b48 (cause 16)
```

Interpretation:

| Observation | Meaning |
|---|---|
| `result 6` | `HAEUN_VM_STEP_LIMIT` |
| No `guest halted` | Guest did not execute architectural `halt` via EXIT path |
| `keys=0` | No Esc (and no digit keys) delivered |
| `frames=39064` | Viewer stayed open for the whole ~10M-step idle run |
| ~3 s wall time | 10M steps complete quickly under YIELD+compose idle |
| `focus_id=0` | Desktop window remained focused |

Same pattern was previously recorded in `docs/m21-manual-validation.md` for `--apps --persist --viewer` without `--input` (`frames=39064` then STEP_LIMIT).

Contrast: with `--input`, Esc is scripted and the log shows `guest halted … r1=0x00000000` (true shutdown).

## Root cause (final)

**`VM_BUDGET_EXHAUSTION`**

`haeun-vm` always passes a fixed `INSTRUCTION_BUDGET` of **10,000,000** steps into `haeun_vm_viewer_run`. The M21 desktop idle loop (`EVENT_POLL` → `YIELD`) legitimately consumes that budget in a few seconds with no Esc. The host then returns `HAEUN_VM_STEP_LIMIT` (6), prints `guest stopped with result 6`, and `DestroyWindow` closes the GUI—while the guest never took the Esc/`EXIT(0)` shutdown path.

Design expectation (“run until Esc”) is **not** implemented by the host budget policy for interactive `--viewer` without a larger/unlimited step cap.
