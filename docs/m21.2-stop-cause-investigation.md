# M21.2 Guest Stop Cause Investigation

Date: 2026-11-15  
Mode: **READ-ONLY** (no source modifications).

Reported stop:

```text
guest stopped with result 6 at PC 0x00100b44 (cause 16)
```

(Also observed nearby: `PC 0x00100b48` under the same command — same loop, adjacent instruction.)

Viewer context: ~39,064 frames before stop (`--apps --persist --viewer`, no `--input`).

---

## 1. Exact stop printer and meanings

### Printer

`src/main.c` after `haeun_vm_viewer_run` (or other run paths):

```c
if (result == HAEUN_VM_HALTED) {
    printf("guest halted after %llu instructions; r1=0x%08x\n", ...);
    rc = 0;
} else {
    fprintf(stderr,
            "guest stopped with result %u at PC 0x%08x (cause %u)\n",
            (unsigned)result, vm.pc, vm.cause);
    rc = 1;
}
```

So this message means: run ended with a host result **other than** `HAEUN_VM_HALTED`.

### `result 6`

`include/haeun/vm.h`:

```c
typedef enum {
    HAEUN_VM_OK = 0,
    HAEUN_VM_HALTED,           /* 1 */
    HAEUN_VM_TRAP,             /* 2 */
    HAEUN_VM_ILLEGAL_INSTRUCTION, /* 3 */
    HAEUN_VM_MEMORY_FAULT,     /* 4 */
    HAEUN_VM_ALIGNMENT_FAULT,  /* 5 */
    HAEUN_VM_STEP_LIMIT,       /* 6 */
    HAEUN_VM_BAD_ARGUMENT
} haeun_vm_result;
```

**`result 6` = `HAEUN_VM_STEP_LIMIT`.**

Assigned when the cooperative viewer loop exhausts `max_steps` while the last step was still `HAEUN_VM_OK`:

`src/vm_viewer_win32.c` `haeun_vm_viewer_run`:

```c
while (*steps_executed < max_steps && !plat.quit) { ... haeun_vm_step ... }
if (!plat.quit && st == HAEUN_VM_OK && *steps_executed >= max_steps)
    st = HAEUN_VM_STEP_LIMIT;
```

`max_steps` comes from `src/main.c`:

```c
#define INSTRUCTION_BUDGET UINT64_C(10000000)
...
result = haeun_vm_viewer_run(&viewer, &vm, INSTRUCTION_BUDGET, &steps);
```

This is a **host policy stop**, not a guest `halt` instruction and not a decoder fault return from `haeun_vm_step`.

### `cause 16`

Architectural interrupt encoding (`src/trap.c` `haeun_trap_try_interrupt`):

```c
haeun_trap_enter(vm, vm.pc, 16u + id, 0u);
```

IRQC source 0 (timer) → cause **16**. Documented in `docs/fault-handling-v1.md`:

| Event | Cause | Handler |
|---|---|---|
| Timer IRQ | 16 | `do_timer` → `pick_next` |

`haeun_trap_enter` also writes `vm->cause = cause` (`src/trap.c`).

**Important distinction (confirmed):** when `viewer_run` returns `HAEUN_VM_STEP_LIMIT`, it does **not** update `vm.cause`. `main.c` prints the **stale** `vm.cause` left from the last trap entry. Seeing `cause 16` therefore means “a timer IRQ was the last recorded trap cause,” **not** “the stop was caused by a timer exception fault.”

There is no stderr `[haeun-fault]` line on this path — consistent with non-fatal IRQ / successful continue until budget.

## 2. Disassembly around PC `0x00100b44`

Linked from process-v1 kernel text (`HXF_BASE = 0x00100000`). Symbols from assembled `kernel/process/proc_sched.s`:

| VA | Symbol region |
|---|---|
| `0x00100aec` | `pick_next` |
| `0x00100b1c` | `pn_scan` |
| `0x00100b40` | `pn_mul` |
| `0x00100b50` | `pn_have` |

Disassembly of ±10 instructions (toolchain `disassemble_bytes` on placed kernel `.text`):

```text
0x00100b1c: pn_scan:   addi r6, r6, 1
0x00100b20:            addi r1, r0, 4
0x00100b24:            cmplt r2, r6, r1
0x00100b28:            bne r2, r0, pn_okidx
0x00100b2c:            addi r6, r0, 0
0x00100b30: pn_okidx:  jal r1, p_pb
0x00100b34:            .word 0x0000A000          ; PCB base literal
0x00100b38: p_pb:      lw r8, 0(r1)
0x00100b3c:            addi r2, r0, 0
0x00100b40: pn_mul:    beq r2, r6, pn_have
0x00100b44:            addi r8, r8, 256          <== STOP PC
0x00100b48:            addi r2, r2, 1
0x00100b4c:            jal r0, pn_mul
0x00100b50: pn_have:   lw r1, 0(r8)
0x00100b54:            addi r2, r0, 1
0x00100b58:            beq r1, r2, pn_found
0x00100b5c:            addi r2, r0, 2
0x00100b60:            beq r1, r2, pn_found
0x00100b64:            addi r5, r5, 1
0x00100b68:            addi r1, r0, 4
0x00100b6c:            beq r5, r1, pn_none
```

Source mapping (`kernel/process/proc_sched.s`):

```asm
pn_mul:
    beq r2, r6, pn_have
    addi r8, r8, 0x100      ; VA 0x00100b44 — PCB stride advance
    addi r2, r2, 1
    jal r0, pn_mul
pn_have:
    lw r1, 0(r8)
    ...
```

Raw word at stop: `0x1e200100` → ADDI `r8, r8, 256`.

### Does PC point at the faulting instruction?

**No fault.** After each successful `haeun_vm_step`, PC is the **next** instruction to execute (`src/vm.c`). When the budget check ends the viewer loop with `st == HAEUN_VM_OK`, `vm.pc` is the instruction that **would have run next**.

Here that next instruction is `addi r8, r8, 0x100` inside a healthy `pick_next` PCB walk — evidence the guest was mid-scheduler, not mid-illegal-op.

## 3. Execution path to the stop

### Guest persistent loop (still active)

`userland/desktop.s`:

1. `loop`: `EVENT_POLL` (27); empty → `idle`.
2. `idle`: `GFX_COMPOSE` (23) → `YIELD` (10) → `jal r0, loop`.
3. Esc-only `shutdown` / create-fail `die` not taken (`keys=0`, no `guest halted`).

### How PC lands in `pick_next`

Two normal kernel entries call `pick_next` (both consistent with idle + timer):

| Path | File | Notes |
|---|---|---|
| `sys_yield` | `kernel/process/proc_sys.s` | Desktop idle YIELD |
| `do_timer` | `kernel/process/proc_trap.s` | Timer IRQ cause 16 → schedule |

`pick_next` → `pn_scan` / `pn_okidx` → `pn_mul` walks PCB slots by `+0x100`. Host budget expires while that loop is running → stop at `0x00100b44` (or `0x00100b48` on another run).

### Viewer frame count

`VIEW_SLICE = 256` steps per pump/blit (`src/vm_viewer_win32.c`).  
~10,000,000 / 256 ≈ 39,062.5 → **~39,064 frames** matches budget exhaustion, not an abrupt guest crash.

Exact stop path:

```text
desktop idle (EVENT_POLL empty)
  → YIELD and/or timer IRQ (cause 16 recorded)
    → pick_next / pn_mul
      → host steps_executed hits INSTRUCTION_BUDGET (10_000_000)
        → haeun_vm_viewer_run sets HAEUN_VM_STEP_LIMIT
          → DestroyWindow
            → main prints "guest stopped with result 6 ... (cause 16)"
```

## 4. Persistence behavior checks

| Question | Finding | Evidence |
|---|---|---|
| Desktop loop still running at stop? | **Yes** | PC in `pick_next` serving YIELD/timer; not `shutdown`/`die` |
| App exit kills desktop? | **No** (this run) | No `app-env: spawn` in idle log |
| Esc misinterpreted as shutdown? | **No** | `keys=0`; would print `guest halted` + result 1 if halted |
| Scheduler invalid / deadlock? | **No** | Mid-`pn_mul` advancing PCBs; READY desktop still schedulable |
| Exception in EVENT_POLL / switch? | **No as stop cause** | Stop result is STEP_LIMIT; no `[haeun-fault]` |
| Illegal insn / bad memory? | **No** | Those yield results 3/4/5 via `haeun_vm_step`, not 6 |

---

## 5. Root cause classification

**Primary: host `VM_BUDGET_EXHAUSTION` / `HAEUN_VM_STEP_LIMIT`.**

- Confirmed stop mechanism: `INSTRUCTION_BUDGET` → `HAEUN_VM_STEP_LIMIT` (result 6).
- Confirmed PC: healthy `pick_next` `pn_mul` (`addi r8,r8,256`).
- Confirmed `cause 16`: stale **timer IRQ** cause field, not the reason `main` took the “stopped” branch.

Not: guest loop EXIT, Esc shutdown, illegal instruction, page fault, or scheduler deadlock.

| Item | Status |
|---|---|
| Result 6 = `HAEUN_VM_STEP_LIMIT` | **Confirmed** (`vm.h`, `vm_viewer_win32.c`, `main.c`) |

| PC = next insn after successful steps | **Confirmed** (`vm.c` step + viewer loop) |
| Cause 16 = timer IRQ encoding | **Confirmed** (`trap.c`, `fault-handling-v1.md`) |
| Cause 16 is stale at STEP_LIMIT print | **Confirmed** (STEP_LIMIT path does not set `vm.cause`) |
| Exact last entry was YIELD vs `do_timer` | **Hypothesis** — both call `pick_next`; cause 16 proves timer trapped at least once earlier; either path is normal idle |
| Wall-clock “few seconds” ≈ 10M YIELD-heavy steps | **Confirmed** by frame math and prior M21.1 timed run (~3 s) |

## 7. Recommended minimal fix (not implemented)

Do **not** change ABI or ISA. Options (smallest first):

1. **Interactive persist viewer:** when `--persist` and `--viewer` (and typically no finite smoke intent), pass an effectively unbounded step budget (e.g. `UINT64_MAX`) into `haeun_vm_viewer_run`, still stopping on `HAEUN_VM_HALTED` (Esc/`EXIT`) or window close (`plat.quit`).
2. Or add CLI `--max-steps N` / `--unlimited` so interactive desktop is explicit.
3. Optional clarity: on `STEP_LIMIT`, print that the host budget ended and avoid implying `cause` was the fault reason (or print `csr_cause` separately).

Automated tests that rely on finite budget + Esc script (`--persist --input`) can keep the current 10M budget.

---

## Summary

The guest did **not** crash at `0x00100b44`. The host stopped stepping after 10M instructions while the kernel was inside `pick_next`’s PCB walk (`addi r8, r8, 256`). `cause 16` is the leftover timer-IRQ cause register value. Viewer frame count (~39k) matches that budget. Persistence fails for interactive use because **host step limit ≠ Esc shutdown**.
