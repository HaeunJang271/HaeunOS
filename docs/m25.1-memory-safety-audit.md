## Findings

### Process isolation (MMU)

| Topic | Class | Evidence |
|-------|-------|----------|
| Separate L0 per AS; user needs `U` | Mitigated | `proc_boot.s` maps; `mmu-v1.md`; M15 isolation tests |
| Cross-AS execute/read of foreign code PA via wrong PT | Mitigated when PTE remapped | SPAWN writes slot-local code PTE (`app_env.c`) |
| Boot `fill_u` maps VA `0x108000` → PA `0x108000` on slots 1–2 | **Potential risk** for FORK | Until SPAWN remaps or scrub clears PTE, slot1/2 share init code PA (`proc_boot.s` `fill_u`) |
| User code PTE non-writable | Mitigated | flags `0x1b` (no W); RO write → fault (M17) |

### Bad address / faults

| Topic | Class | Evidence |
|-------|-------|----------|
| Unmapped VA → page fault → ZOMBIE + host reap | Mitigated | `sys_fault_exit`, `ecall_mux_on_fault`, M17 tests |
| Bare OOB physical | Mitigated | MMU/bare fault causes (`mmu-v1.md`) |

### Stack overflow

| Topic | Class | Evidence |
|-------|-------|----------|
| Single 4 KiB user stack; no guard page | **Confirmed limitation** | One ustack PTE per slot; no stack-limit check in trap path |
| Deep call / large frame can corrupt adjacent PA | **Potential risk** | Slot0 top `0x114000` is slot1 stack page base — overflow past top walks into next page if mapped elsewhere; user stack grows down within page only if software respects base |

Within one page, overflow stays in that page’s RAM (zeros/data), not a classic guard-page SEGV unless adjacent PTE is absent. Slot stacks are **adjacent** in PA (`0x113000`, `0x114000`, `0x115000`): overflowing **below** `ustack_base` is still inside the same page; overflowing **above** top is a different VA that may fault or hit another mapping.

### Heap collisions

| Topic | Class | Evidence |
|-------|-------|----------|
| Guest heap | **N/A** | No process-v1 heap |
| Window backing vs code | Mitigated by pool bound | Pool HI `0x100000` &lt; code `0x108000` (`gfx_wm.h`) |

### AS reuse / residual data

| Topic | Class | Evidence |
|-------|-------|----------|
| SPAWN wipe code+stack before load | Mitigated | `memset` then `memcpy` in `haeun_app_spawn` |
| EXIT scrub code+stack+PTE | Mitigated for SPAWN slots 1–2 | `scrub_slot` |
| Slot 0 never scrubbed on reap | **Confirmed limitation** | `scrub_slot` requires `slot >= 1` |
| FORK child without SPAWN scrub | **Confirmed limitation** | No code copy; may fault (PTE=0) or see stale/shared mapping |
| ZOMBIE PCB until WAIT; pages already scrubbed | Mitigated (SPAWN path) | Dual-stage M24 contract |

### Termination without reclaim

| Topic | Class | Evidence |
|-------|-------|----------|
| SPAWN app EXIT | Mitigated | host `app_reap` + guest WAIT/TRYWAIT/SPAWN memset |
| FORK-only child EXIT | **Potential risk** | No `runs[]` → no `scrub_slot`; pages reused only when slot recycled by SPAWN/FORK metadata |

### FORK consistency

| Topic | Class | Evidence |
|-------|-------|----------|
| Not a POSIX memory clone | **Confirmed limitation** | `proc_fork.s` copies PCB/GPRs only |
| Parent/child diverge immediately in memory image | Expected under current design | Documented in M24.1 audit |

### SPAWN failure partial alloc

| Topic | Class | Evidence |

### Concurrent AS collision

| Topic | Class | Evidence |

| Topic | Class | Evidence |

### Double free / scrub

| Topic | Class | Evidence |
|-------|-------|----------|
| Second `haeun_app_reap` | Mitigated | returns `NOENT` |

## Confirmed defects (this pass)

No **new** emergency memory-corruption defect was proven beyond the already-fixed M24.4 `TRYWAIT` sec_dispatch issue (not a memory allocator bug).

Primary memory **correctness gaps** are design limitations: FORK≠image copy, no heap, no stack guard, slot0 unscanned scrub, FORK path without `scrub_slot`.
