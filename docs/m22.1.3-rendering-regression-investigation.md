# M22.1.3 Rendering Regression Investigation

> **HISTORICAL probe (M22.2):** Captured while FB was still documented/probed as **64×32** in places. **Current** host FB is **320×180** @ `0x00200000` — [graphics-api.md](graphics-api.md), [m22.1.3-target-desktop.md](m22.1.3-target-desktop.md). Keep this file as the investigation trail that motivated the resolution bump.

**Mode:** read-only (no source fixes in this milestone).  
**Date:** 2026-11-16  
**Probe capture:** `build/m22_1_3_idle_probe.ppm` (+ `.png` at viewer-equivalent ×8).  
**Compare refs:** `docs/m22.1.1-after.png` (post-1.1, glyphs removed), `docs/m22.1.2-idle.png` / current probe (post-1.2, glyphs restored).

## Executive verdict

This is **not** a multi-process / multi-framebuffer duplication bug, and **not** a double-scaling bug in the glyph blitter.

The visual “regression” relative to M22.1.1 is primarily the **intentional M22.1.2 reintroduction of `WIN_DRAW_TEXT` (8×8 glyphs) onto a 64×32 framebuffer**, then displayed with **viewer `scale = 8`**. That combination makes:

- each character occupy **⅛ of FB height** and **⅛ of FB width**;
- three shortcut columns look like **three separate mini-UIs**;
- dark wallpaper (`0x00101828`) read as “mostly black”;
- taskbar read as more large text (`Start`, `12`) rather than a distinct chrome strip.

Quantitative probe: `black_count = 0`, bright glyph pixels ≈ 665/2048, three distinct tile hues at `(4,10)/(24,10)/(44,10)`. Terminal idle runs show **no** `app-env: spawn` and `focus_id=0` (single shell window).

## 2. Duplicate rendering evidence

### Process / window count (idle)

| Question | Answer | Evidence |
|---|---|---|
| How many desktop shells? | **One** PCB0 guest | `desktop.s` creates one window; loop does not `APP_SPAWN` unless key/click |
| How many apps draw at idle? | **Zero** | Probe / composition tests assert no `app-env: spawn`; operator `--viewer` logs in `terminals/1.txt` show keys only, `focus_id=0` |
| Shared vs private FB? | **One primary FB** | `HAEUN_GUI_FB_BASE=0x10000`, 64×32 — `include/haeun/vm_gui_host.h`; windows have private **backings**, compose blits into FB |
| Viewer multi-buffer? | **No** | `refresh_fb` → optional `chrome_present` → one `haeun_fb_view_snapshot_bgra` → `StretchDIBits` — `src/vm_viewer_win32.c` |
| Shell launched twice? | **No evidence** | Single `WIN_CREATE` in `user_init`; NPROC/AS slots unused until spawn |

### Composition path (single authoritative blit)

```
guest shell_paint → window backing @ 0x1C000
guest shell_compose (ECALL 23) → haeun_gfx_compose:
    clear FB(desktop_rgba)
    blit visible windows by z   [src/gfx_comp.c]
viewer refresh:
    chrome_present(clear 0x203040FF + blit + paint_one)
    # paint_one returns early for fullscreen shell [src/gfx_chrome.c]
```

**“Three compositions”** = three **shortcut columns** painted into the **same** shell backing (icons at x=4/24/44, labels under them), not three processes.

## 3. Text scaling pipeline (why text looks huge)

### End-to-end

| Stage | Value | Source |
|---|---|---|
| Guest API | `WIN_DRAW_TEXT` ECALL 28 | `include/haeun/sec.h`, `src/m20_ecall.c` |
| Glyph size | **8×8 px**, fixed | `HAEUN_GFX_UI_GLYPH = 8` in `include/haeun/gfx_ui.h` |
| Glyph bits | `haeun_gfx_font8_rows` | `src/gfx_font.c` |
| Advance | `cx += 8` per char; line `cy += 8` | `draw_text_win` in `src/gfx_ui.c` |
| bg=0 | off-pixels skipped (transparent) | `haeun_gfx_ui_draw_char` |
| Guest FB | 64×32 | `HAEUN_GUI_FB_WIDTH/HEIGHT` |
| Viewer scale | **8** (integer nearest-neighbor) | `viewer->scale = 8` / `StretchDIBits` in `src/vm_viewer_win32.c` |
| Mouse map | `fb_x = lx / scale` | `src/fb_view.c` — same scale, not applied twice to glyphs |

### Scale math (no double font scale)

| Quantity | FB pixels | On-screen (×8) |
|---|---|---|
| One glyph | 8×8 | **64×64** |
| `"HAEUN"` | 40×8 | 320×64 |
| `"Start"` | 40×8 | 320×64 |
| Fraction of FB height per line | 8/32 = **25%** | same |
| Fraction of FB width per char | 8/64 = **12.5%** | same |

There is **no** second multiply inside `haeun_gfx_ui_draw_text`. Enlargement is **(fixed 8×8 font) × (FB tiny) × (viewer ×8)**.

### Glyph orientation check (probe)

Against font `H` row0=`0x33`, row3=`0x3F` at origin `(1,0)`:

- row0 on-bits at glyph cols 2,3,6,7 → observed bright pattern matches upright bitmap.
- Vision descriptions calling text “upside-down/mirrored” are inconsistent with this bit check; chunky 8×8 at ×8 is easy to misread.

### Clipping

`draw_text_win` wraps if `cx + 8 > win->w`, clips via `put_pixel` OOB. Shell window is full 64×32, so `"Fil"` near x=40 can clip the last columns of the FB edge — contributes to “overflow” appearance, not a second scaler.

## 4. Window geometry (idle vs when apps open)

### Idle (probe / `--viewer` without spawn)

| Role | PID | Win ID (typical) | X,Y | W×H | Z | Owner |
|---|---|---|---|---|---|---|
| Desktop shell | 1 (PCB0) | 0 | 0,0 | 64×32 | topmost (only) | guest desktop |

Host chrome: **not drawn** (fullscreen heuristic in `paint_one`).

**Visible “windows” in the screenshot are not WM windows** — they are rectangles + glyphs inside the shell backing:

| Visual column | Icon rect (client) | Label | Meaning |
|---|---|---|---|
| Left | (4,9)–(12,17) + `C` | `Cal` @ (1,17) | Calculator shortcut |
| Mid | (24,9)–(32,17) + `E` | `Ed` @ (26,17) | Editor shortcut |
| Right | (44,9)–(52,17) + `F` | `Fil` @ (40,17) | Files shortcut |

Overlap between columns is **label packing on 64 px width** (intentional layout stress), not z-fighting between processes.

### After spawn (not in idle probe; from app sources)

| App | PID (after spawn) | Create args | Notes |
|---|---|---|---|
| calc | ≥2 | (16,8) 32×16 | `userland/app_calc.s` |
| edit | ≥2 | (18,9) 32×16 | cascade |
| files | ≥2 | (20,10) 32×16 | cascade |
| filemgr | ≥2 | (14,8) 36×16 | key `3` |

These **do** overlap each other and the shell by design when multiple apps are open; host chrome title (`TITLE_H=6`) adds further visual stacking. Idle regression report symptoms do **not** require these windows.

## 5. Minimal rendering test (design only — not implemented)

**Goal:** Prove clear → rect → text → frame without desktop/apps.

**Proposed artifact (future):** `userland/gfx_smoke.s` + `tools/build_process_gfx_smoke.py` + `tests/m22_1_3_gfx_smoke_tests.py`.

**Guest steps (known coords):**

1. `WIN_CREATE` (0,0) 64×32 backing `0x1C000` (or smaller 32×16 at (16,8) if isolating chrome).
2. `WIN_FILL` solid `0x00204060`.
3. Pixel-loop or fill helper: rectangle `(8,8)–(24,16)` color `0x00E08040`.
4. `WIN_DRAW_TEXT` at `(8,18)` string `"Hi"` fg light, bg 0.
5. Optional: 1px border via `WIN_PIXEL` around the rect.
6. `GFX_COMPOSE` with explicit clear `0x00000000` or desktop color.
7. `EXIT(0)`.

**Host run:**

```text
haeun-vm build/gfx_smoke.hxf --gui --desktop --fb-dump build/m22_1_3_smoke.ppm
```

**Pass criteria:**

- Exactly one used WM window (or zero apps spawned).
- PPM: background uniform; rect pixels match; `"Hi"` glyph bits match font at expected origin.
- Viewer ×8 may still look blocky — assert on **FB pixels**, not perceived size.

**Do not** register `--apps` or call `APP_SPAWN`.

## 6. Root cause summary

| Symptom (operator) | Root cause (confirmed / not) |
|---|---|
| Three similar compositions | **Confirmed:** three shortcut columns in one shell paint (M22.1.2), not three shells |
| Large / overflowing text | **Confirmed:** 8×8 glyphs on 64×32 + viewer ×8; 1.2 restored text after 1.1 removed it |
| Window contents overlap | **Idle:** label/column packing. **With apps:** intentional cascade + chrome (separate) |
| Mostly black FB | **Confirmed misread:** dark clear `0x00101828`; probe `black_count=0` |
| No coherent taskbar | **Partial:** taskbar strip + `Start` exist; text-dominated ×8 view hides “bar” affordance |
| Duplicate FB writers | **Not found** |
| Scale applied twice | **Not found** |

**Unresolved / open (would need a fix milestone, not claimed fixed here):**

- Whether product intent is “keep 64×32 + 8×8” (then UI must use far less text) vs “raise FB resolution / add smaller font” (ABI/host change).
- Whether viewer should default to a lower integer scale for readability during development.

## 7. Recommended minimal repair sequence (do not implement in M22.1.3)

1. **Land gfx smoke test** (§5) and keep it green as a pipeline canary.  
2. **Decide density budget:** e.g. max one text row of ≤8 glyphs in idle chrome, or 4×4/5×5 font if ABI allows.  
3. **Desktop paint pass:** reduce simultaneous `WIN_DRAW_TEXT` (title **or** labels **or** Start — not all full-width); keep colored tiles as the primary shortcut affordance.  
4. **Taskbar affordance:** wider/taller distinct fill, short mark (`S`) instead of `"Start"` if staying on 8×8/64.  
5. **Viewer:** optional `--scale N` (document that ×8 turns 8px glyphs into 64px blocks).  
6. **Only then** revisit app cascade/chrome if multi-app screenshots still confuse operators.  
7. Re-capture idle PPM/PNG and compare to `m22_1_3_idle_probe` / `m22.1.1-after`.
